### 1. В чем разница между Fetch API и XMLHttpRequest? Какие преимущества предоставляет Fetch API?
| Критерий | `XMLHttpRequest` (XHR) | `Fetch API` |
| :--- | :--- | :--- |
| Парадигма работы | Основан на событиях и колбэках (`onload`, `onerror`, `onreadystatechange`). Ведет к «callback hell». | Построен на современных **Promise** (промисах), нативно поддерживает синтаксис `async/await`. |
| Синтаксис и читаемость | Громоздкий, низкоуровневый boilerplate-код. | Лаконичный, модульный интерфейс (`fetch(url, options)`). |
| Архитектура объектов | Один монолитный объект `XMLHttpRequest` совмещает отправку, получение, заголовки и состояние. | Раздельные стандартизированные абстракции: `Request`, `Response`, `Headers`, `Body`. |
| Работа с потоками (Streams) | Данные загружаются в память целиком до окончания запроса. | Поддерживает `ReadableStream`, позволяя обрабатывать тело ответа чанками по мере поступления. |
| Поддержка в Service Workers | XHR запрещен в Service Workers. | Fetch является базовым сетевым стандартом для Service Workers и PWA. |

### 2. Как обрабатываются ошибки в Fetch API и почему ответ с HTTP статусом 404 не вызывает reject промиса?
В спецификации WHATWG Fetch промис, возвращаемый функцией `fetch()`, переходит в состояние rejected (отклонен) исключительно при критических сбоях сетевого уровня:
- Полное отсутствие интернет-соединения;
- Ошибка разрешения доменного имени (DNS lookup failure);
- Блокировка запроса политикой CORS (Cross-Origin Resource Sharing);
- Истечение времени ожидания или ручная отмена через `AbortController`.

Если сервер физически ответил клиенту и вернул валидный HTTP-пакет со статусом `404 Not Found`, `401 Unauthorized` или `500 Internal Server Error`, с точки зрения сетевого стека HTTP-транзакция успешно состоялась. Поэтому промис успешно резолвится объектом `Response`.

Правильный паттерн обработки:
```javascript
try {
  const response = await fetch('/api/data');
  // Обязательная ручная проверка флага response.ok (статусы 200–299)
  if (!response.ok) {
    throw new Error(`HTTP ошибка! Статус: ${response.status} (${response.statusText})`);
  }
  const data = await response.json();
} catch (error) {
  // Сюда попадут как сетевые сбои, так и выброшенные вручную HTTP-ошибки
  console.error('Ошибка запроса:', error.message);
}
```

### 3. Какие методы HTTP поддерживает Fetch API и в каких случаях используется каждый из них?
Fetch поддерживает все стандартные методы HTTP:
1. GET - запрос данных с сервера без изменения его состояния (идемпотентный и безопасный). Параметры передаются в строке запроса (`query params`).
2. POST - создание нового ресурса или отправка конфиденциальных данных в теле запроса (не идемпотентный).
3. PUT - полная замена существующего ресурса данными из тела запроса (идемпотентный).
4. PATCH - частичная модификация ресурса (передаются только те поля, которые нужно изменить).
5. DELETE - удаление указанного ресурса (идемпотентный).
6. HEAD - аналогичен GET, но сервер возвращает только заголовки без тела ответа (используется для проверки существования файла, даты изменения или размера через `Content-Length`).
7. OPTIONS - запрос доступных методов коммуникации с сервером (используется браузером для preflight CORS-запросов).

### 4. Как работать с заголовками запроса и ответа в Fetch API? Приведите примеры полезных заголовков.
Для заголовков используется специальный интерфейс `Headers`:
```javascript
const myHeaders = new Headers();
myHeaders.append('Content-Type', 'application/json');
myHeaders.append('Authorization', 'Bearer eyJhbGciOi...');

// Чтение заголовков ответа:
const response = await fetch('/api/data', { headers: myHeaders });
console.log(response.headers.get('Content-Type')); // например, "application/json; charset=utf-8"
```

Ключевые заголовки:
- `Content-Type` указывает формат передаваемых данных (`application/json`, `multipart/form-data`, `application/x-www-form-urlencoded`).
- `Accept` сообщает серверу, какие типы контента ожидает клиент (`application/json, text/plain, */*`).
- `Authorization` передача учетных данных (токены `Bearer`, `Basic`).
- `Cache-Control` управление кэшированием браузера и прокси (`no-cache`, `max-age=3600`).
- `X-Requested-With` пользовательский заголовок для маркировки AJAX-запросов.

### 5. В чем разница между PUT и PATCH запросами и когда следует использовать каждый метод?
- PUT (Полная замена) - клиент отправляет полную модель ресурса. Если в отправленном объекте отсутствуют какие-либо старые поля, сервер обязан удалить или обнулить их.
- PATCH (Частичное изменение) - клиент отправляет только те поля, которые требуется изменить (дельта-обновление). Сервер объединяет полученные данные с уже существующими.

Если у пользователя есть поля `{ id: 1, name: "Иван", email: "ivan@ya.ru", role: "admin" }`, то:
- Запрос `PATCH /users/1` с `{ name: "Петр" }` обновит только имя, оставив email и role без изменений.
- Запрос `PUT /users/1` с `{ name: "Петр" }` затрет email и role (сделает их null или сбросит в дефолтные значения).

### 6. Как реализовать авторизацию в Fetch API (Basic Auth, Bearer Token, OAuth2)?
1. Bearer Token (JWT):
   ```javascript
   fetch('/api/profile', {
     headers: {
       'Authorization': `Bearer ${token}`
     }
   });
   ```
2. Basic Authentication (Логин + Пароль):
   Логин и пароль объединяются через двоеточие и кодируются в base64 с помощью функции `btoa`:
   ```javascript
   const credentials = btoa('username:password');
   fetch('/api/secure', {
     headers: {
       'Authorization': `Basic ${credentials}`
     }
   });
   ```
3. OAuth2 / Refresh Token Flow:
   При получении ответа `401 Unauthorized` интерцептор перехватывает ошибку, выполняет POST-запрос на эндпоинт `/auth/refresh` с сохраненным `refreshToken`, получает новую пару токенов, сохраняет их и повторяет исходный запрос пользователя.

### 7. Какие способы отмены запросов существуют в Fetch API и когда их следует использовать?
Отмена запросов реализуется с помощью глобального интерфейса `AbortController`:

```javascript
const controller = new AbortController();

const fetchPromise = fetch('/api/heavy-data', {
  signal: controller.signal
});

// Отмена запроса в любой момент:
controller.abort();
```

Когда отмена необходима:
1. Поиск с подсказками
2. Размонтирование React-компонента
3. Реализация жесткого сетевого таймаута

### 8. Как работать с разными форматами данных (JSON, FormData, Blob, ArrayBuffer) в Fetch API?
Объект `Response` предоставляет набор встроенных методов для чтения тела ответа:
1. JSON (`response.json()`): парсит тело ответа в JavaScript-объект.
2. Текст (`response.text()`): возвращает сырую строку (HTML, plain text, XML, CSV).
3. Blob (`response.blob()`): читает бинарные данные (изображения, аудио, PDF-документы). С помощью `URL.createObjectURL(blob)` можно отобразить файл в DOM или сгенерировать ссылку для скачивания.
4. FormData (`new FormData()`) используется для отправки файлов и полей форм с кодировкой `multipart/form-data`. Важно: при отправке `FormData` заголовок `Content-Type` задавать вручную нельзя, браузер сам выставляет правильный boundary.
5. ArrayBuffer (`response.arrayBuffer()`): низкоуровневый массив байт в памяти для WebGL, WebAssembly, обработки аудио в Web Audio API.

### 9. Как оптимизировать производительность при работе с множественными запросами?
1. Вместо последовательного ожидания через `await` несвязанные запросы запускаются параллельно через `Promise.all()`:
   ```javascript
   const [users, posts] = await Promise.all([
     fetch('/api/users').then(r => r.json()),
     fetch('/api/posts').then(r => r.json())
   ]);
   ```
2. Кэширование на клиенте (In-Memory / IndexedDB / Cache API) - cохранение результатов запросов в структуру `Map` с таймштампом и временем жизни (TTL) для предотвращения повторных обращений к серверу.
3. Ограничение частоты сетевых вызовов при вводе текста или прокрутке страницы.
4. Использование одного TCP/QUIC-соединения для множества параллельных запросов без блокировки начала очереди.

### 10. Какие лучшие практики существуют для работы с Fetch API в production приложениях?
1. Единый HTTP-клиент: никогда не вызывать «голый» `fetch` напрямую в UI-компонентах. Создавать модуль с базовым URL, автоматической подстановкой токенов и заголовков.
2. Унифицированная обработка ошибок, всегда проверять `response.ok` и парсить тело ошибки сервера (`const errorData = await response.json()`).
3. Предотвращать зависание соединений при «мертвых» прокси с помощью `AbortSignal.timeout(ms)` или `AbortController` благодаря выставлению таймаутов.
4. при сетевых ошибках или кодах `502/503/504` повторять запрос с возрастающей задержкой.
5. Использовать TypeScript или runtime-валидацию схем (Zod) для валидации структуры данных от внешних API.
