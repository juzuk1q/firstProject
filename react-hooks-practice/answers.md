# Ответы на вопросы для самоконтроля: Практическая работа №16 («React: использование хуков»)

---

### 1. В чем разница между useState и useReducer? Когда использовать каждый?

| Критерий | `useState` | `useReducer` |
| :--- | :--- | :--- |
| **Сложность состояния** | Подходит для простых примитивов (числа, строки, булевы флаги) или независимых полей. | Идеален для сложного состояния (вложенные объекты, массивы объектов, взаимосвязанные поля). |
| **Логика обновления** | Логика обновления пишется прямо в компоненте или обработчиках событий. | Вся бизнес-логика перехода состояний вынесена в чистую функцию-редьюсер (`reducer(state, action)`). |
| **Предсказуемость и тестирование**| При множестве изменений логика может «размазываться» по коду компонента. | Легко тестировать редьюсер отдельно от React-компонентов как чистую функцию JavaScript. |
| **Оптимизация передачи** | Передача функций обновления в дочерние компоненты может вызывать ререндеры (требует обертки в `useCallback`). | Функция `dispatch` стабильна по ссылке на протяжении всей жизни компонента и никогда не меняется. |

**Когда использовать:**
- **`useState`**: для изолированных состояний: открыто/закрыто модальное окно, значение одного инпута, счетчик, текущая вкладка переключателя.
- **`useReducer`**: когда следующее состояние зависит от сложной комбинации предыдущего состояния и типа действия (например, корзина интернет-магазина, форма со сложными зависимостями валидации, конечные автоматы/стейт-машины, секундомер/таймер).

### 2. Как работает массив зависимостей в useEffect? Что произойдет если его не указать?

Хук `useEffect(callback, dependencies)` управляет выполнением побочных эффектов:
1. **Массив зависимостей не передан (`useEffect(cb)`)**:
   - Эффект выполняется после **каждого** рендера компонента (при монтировании и при любом изменении любого `props` или `state`).
   - Если внутри эффекта вызывается изменение состояния без условий, возникнет **бесконечный цикл ререндеров** и падение браузера.
2. **Передан пустой массив (`useEffect(cb, [])`)**:
   - Эффект выполняется строго **один раз** при первом монтировании компонента в DOM.
   - Функция очистки (cleanup) выполнится только один раз при размонтировании компонента.
3. **Передан массив с переменными (`useEffect(cb, [propA, stateB])`)**:
   - React сравнивает текущие значения зависимостей со значениями на предыдущем рендере с помощью алгоритма `Object.is()`.
   - Эффект перезапустится только тогда, когда хотя бы одна из указанных зависимостей изменилась.

### 3. Что такое "stale closure" (устаревшее замыкание) в хуках и как использовать функциональные обновления чтобы избежать этой проблемы?

**Stale closure** — это ситуация в JavaScript, когда функция замыкает переменные из контекста своего создания, и при последующих рендерах продолжает ссылаться на старые (неактуальные) значения этих переменных, потому что не была пересоздана.

**Пример проблемы:**
```javascript
useEffect(() => {
  const timer = setInterval(() => {
    // Здесь count замкнут со значением 0! 
    // На каждом тике setCount(0 + 1) будет всегда устанавливать 1
    setCount(count + 1);
  }, 1000);
  return () => clearInterval(timer);
}, []); // пустой массив зависимостей
```

**Решение — функциональное обновление:**
Передать функцию обратного вызова в `setCount(prev => prev + 1)`:
```javascript
useEffect(() => {
  const timer = setInterval(() => {
    // React сам передает самое свежее актуальное значение в аргумент prev
    setCount(prev => prev + 1);
  }, 1000);
  return () => clearInterval(timer);
}, []);
```
Таким образом, эффект не нуждается в значении `count` из внешнего замыкания, а интервал не перезапускается каждый раз.

### 4. Когда действительно нужны useCallback и useMemo? Не являются ли они преждевременной оптимизацией?

Хуки `useMemo` (кеширование результата вычислений) и `useCallback` (кеширование ссылки на функцию) не делают код быстрее «по умолчанию». Сама проверка зависимостей и сохранение в памяти также имеют накладные расходы. В большинстве случаев базовые операции в JS (фильтрация сотни элементов) выполняются за доли миллисекунды, поэтому их оборачивание — преждевременная оптимизация.

**Когда они действительно необходимы:**
1. **Тяжелые вычислительные операции**: сложные математические расчеты, преобразование больших массивов данных (тысячи элементов), парсинг или шифрование (`useMemo`).
2. **Предотвращение ререндеров оптимизированных дочерних компонентов**: когда функция или объект передаются пропсом в дочерний компонент, обернутый в `React.memo`. Если не использовать `useCallback`, ссылка на функцию обновляется на каждый рендер родителя, и `React.memo` становится бесполезным.
3. **Сохранение стабильности ссылок для зависимостей других хуков**: если функция или объект входят в массив зависимостей `useEffect`, `useCallback` предотвратит бесконечные или лишние повторные вызовы эффекта.

### 5. Как useRef отличается от useState? В каких сценариях useRef незаменим?

| Свойство | `useState` | `useRef` |
| :--- | :--- | :--- |
| **Вызов рендера** | Изменение значения через `setState` **всегда инициирует повторный рендер** компонента. | Изменение свойства `.current` происходит мутабельно и **не вызывает** ререндер. |
| **Синхронность** | Обновление состояния асинхронно/батчится React. | Значение в `.current` обновляется синхронно и доступно сразу на следующей строчке. |
| **Назначение** | Хранение данных, которые влияют на визуальное отображение интерфейса. | Хранение мутабельных значений, «переживающих» рендеры, или прямых ссылок на DOM-элементы. |

**Сценарии, где `useRef` незаменим:**
1. **Прямой доступ к DOM-узлам**: установка фокуса на поле ввода (`inputRef.current.focus()`), прокрутка страницы к элементу (`scrollIntoView`), воспроизведение медиа (`videoRef.current.play()`).
2. **Хранение идентификаторов таймеров и интервалов**: сохранение ID от `setTimeout`/`setInterval` для их последующей очистки.
3. **Отслеживание предыдущего значения пропсов или состояния**: чтение того, каким было значение на прошлом рендере (`prevValue.current = value`).
4. **Флаги жизненного цикла**: например, флаг `isMounted` для предотвращения вызова `setState` после размонтирования компонента.

### 6. Какие правила хуков существуют и почему их нельзя нарушать?

Существуют два основополагающих правила хуков:
1. **Вызывайте хуки только на верхнем уровне**:
   - Нельзя вызывать хуки внутри циклов (`for`, `while`), условных операторов (`if`, `switch`) или вложенных функций.
2. **Вызывайте хуки только из функций React**:
   - Хуки разрешено вызывать только из функциональных компонентов React или из пользовательских (кастомных) хуков. Их нельзя вызывать в обычных JS-функциях или классовых компонентах.

**Почему их нельзя нарушать?**
React внутри не использует имена переменных хуков. Он хранит состояние хуков в виде **связного списка или массива**, привязанного к волокну (Fiber) конкретного компонента. Позиция (индекс) вызова хука при рендере определяет, какое именно состояние ему вернуть. Если хук будет вызван внутри `if`, порядок вызовов изменится, внутренний указатель сместится, и состояние одного хука запишется в другой, что приведет к трудноуловимым багам и краху приложения.

### 7. Как создать кастомный хук и какие лучшие практики следует соблюдать?

Кастомный хук — это обычная JavaScript-функция, имя которой начинается с префикса **`use`**, и которая внутри вызывает другие встроенные или кастомные хуки React.

**Лучшие практики:**
1. **Префикс `use` обязателен**: это позволяет линтерам (`eslint-plugin-react-hooks`) проверять соблюдение правил хуков.
2. **Чистая ответственность**: хук должен инкапсулировать одну конкретную логику (например, работа с сетью `useFetch`, подписка на событие `useEventListener`, сохранение в хранилище `useLocalStorage`).
3. **Возвращайте удобный интерфейс**: кортеж `[value, setter]` (как в `useState`) если результат состоит из 2 элементов, либо понятный объект `{ data, loading, error, refetch }` при возврате нескольких параметров.
4. **Обязательно очищайте ресурсы**: в `useEffect` внутри хука всегда возвращайте функцию очистки таймеров, слушателей событий (`removeEventListener`) или контроллеров отмены запроса (`AbortController`).
5. **Мемоизируйте возвращаемые колбэки**: если хук возвращает функции (например, `toggle`, `reset`), оборачивайте их в `useCallback`.

### 8. В чем преимущества использования useContext перед передачей props через несколько компонентов?

Проблема передачи данных через цепочку промежуточных компонентов называется **«prop drilling»**.

**Преимущества `useContext`:**
- **Чистый код промежуточных компонентов**: компонентам на средних уровнях дерева больше не нужно знать о данных, которые им не требуются, и пробрасывать их ниже.
- **Глобальные параметры доступны везде**: идеальное решение для глобального состояния интерфейса: тема оформления (светлая/темная), текущий язык локализации (ru/en), данные авторизованного пользователя, конфигурация темы.
- **Упрощение рефакторинга**: добавление нового потребителя контекста в глубине дерева не требует изменения десятков промежуточных файлов.
- **Легкая масштабируемость**: можно создавать несколько независимых контекстов под разные предметные области (UserContext, ThemeContext, CartContext).

### 9. Как обрабатывать асинхронные операции в кастомных хуках?

В React сам колбэк в `useEffect` не может быть объявлен как `async` (`useEffect(async () => ...)` запрещено), так как `useEffect` ожидает возврат либо функции очистки (`cleanup`), либо `undefined`, а async-функция возвращает `Promise`.

**Правильный паттерн:**
```javascript
function useFetch(url) {
  const [data, setData] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    // 1. Создаем контроллер отмены для сетевых запросов
    const controller = new AbortController();
    let isMounted = true;

    const execute = async () => {
      setLoading(true);
      setError(null);
      try {
        const response = await fetch(url, { signal: controller.signal });
        if (!response.ok) throw new Error(`HTTP error: ${response.status}`);
        const result = await response.json();
        if (isMounted) setData(result);
      } catch (err) {
        if (err.name !== 'AbortError' && isMounted) {
          setError(err.message);
        }
      } finally {
        if (isMounted) setLoading(false);
      }
    };

    execute();

    // 2. Функция очистки отменяет незавершенный запрос
    return () => {
      isMounted = false;
      controller.abort();
    };
  }, [url]);

  return { data, loading, error };
}
```

### 10. Какие способы отладки хуков вы знаете?

1. **React Developer Tools (расширение для браузера)**:
   - Вкладка **Components**: показывает все используемые хуки компонента, их текущие значения (State, Reducer, Memo, Callback), а также позволяет динамически изменять значения состояния в реальном времени.
   - Вкладка **Profiler**: позволяет замерить время рендеринга и понять, какой именно хук или пропс вызвал повторный рендер компонента.
2. **Встроенный хук `useDebugValue`**:
   - Специально предназначен для форматирования и вывода пользовательских меток в React DevTools для кастомных хуков (например, `useDebugValue(isOnline ? 'Online' : 'Offline')`).
3. **Логирование через `console.log` внутри эффектов**:
   - Добавление `console.log('Эффект перезапущен, зависимость изменилась:', dep)` позволяет точно увидеть момент пересчета.
4. **ESLint правила (`eslint-plugin-react-hooks`)**:
   - `react-hooks/rules-of-hooks`: проверяет вызов хуков на верхнем уровне.
   - `react-hooks/exhaustive-deps`: автоматически предупреждает о пропущенных зависимостях в `useEffect`, `useCallback`, `useMemo`.
5. **Точки останова (debugger)**:
   - Использование директивы `debugger` внутри кастомных хуков или редьюсеров для пошаговой трассировки в инструментах разработчика браузера (DevTools Sources).
