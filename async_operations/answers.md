## 1. В чем разница между `Promise.then().catch()` и `async/await` с `try/catch`? Когда следует использовать каждый подход?
`Promise.then().catch()`:
  * Основан на явном вызове методов цепочки промисов.
  * Возвращает новый промис на каждом шаге.
  * Недостатки: при глубокой зависимости шагов друг от друга может приводить к «Promise Hell» (сложной вложенности коллбэков) и затрудняет совместное использование переменных из разных звеньев цепочки.
  * Когда использовать: отлично подходит для простых линейных цепочек из 1–2 шагов, примитивных фоновых операций («fire-and-forget»), а также внутри функциональных пайплайнов (например, обработка массива промисов).
`async/await` с `try/catch`:
  * Синтаксический сахар над промисами, появившийся в ES2017.
  * Позволяет писать асинхронный код так, будто он синхронный, сохраняя линейный поток чтения снизу вверх.
  * Ошибки отлавливаются стандартной языковой конструкцией `try...catch...finally`, перехватывающей как реджекты промисов, так и обычные синхронные исключения (`TypeError`, `ReferenceError`).
  * Когда использовать: стандарт де-факто для сложной бизнес-логики, условных ветвлений (`if/else`), циклов с последовательным ожиданием (`for...of`), работы с несколькими зависимыми сетевыми запросами и отладки через точки останова.

## 2. Как работает `Promise.all` и что происходит, если один из промисов в массиве завершается ошибкой?
Принцип работы:
  `Promise.all(iterable)` принимает массив (или любую итерируемую коллекцию) промисов и запускает их параллельно.
  Возвращает единый промис, который переходит в состояние `fulfilled` только тогда, когда все переданные промисы успешно завершились. Результирующее значение - массив результатов в том же порядке, в котором промисы были переданы на вход (независимо от того, какой промис завершился раньше по времени).
Поведение при ошибке («Fail-Fast»):
  Если хотя бы один промис завершается ошибкой (reject), `Promise.all` немедленно отклоняется с ошибкой этого первого упавшего промиса. Все остальные промисы продолжают физически выполняться в фоновом режиме браузера, но их результаты игнорируются, а весь составной промис переходит в `rejected`.

## 3. В чем разница между `Promise.all`, `Promise.race` и `Promise.allSettled`? Приведите практические примеры использования каждого.

| Метод | Условие успешного завершения | Поведение при ошибке | Практический пример |
| :--- | :--- | :--- | :--- |
| `Promise.all` | Когда все промисы выполнены успешно. | Завершается ошибкой при первом же сбое (Fail-Fast). | Загрузка данных для дашборда: профиль пользователя + список виджетов + права доступа. Если прав нет, весь дашборд не рендерится. |
| `Promise.race` | Завершается сразу, как только любой первый промис перейдет в любое состояние (успех или ошибка). | Если первый завершившийся промис упал, `race` падает вместе с ним. | Реализация сетевого таймаута: гонка реального `fetch(url)` и таймера `delayWithPromise(5000).then(() => { throw new Error('Timeout'); })`. |
| `Promise.allSettled` | Завершается всегда, когда все промисы завершились (независимо от успеха или ошибок). | Никогда не отклоняется целиком. Возвращает массив объектов вида `{ status: 'fulfilled', value }` или `{ status: 'rejected', reason }`. | Массовая рассылка уведомлений / синхронизация 10 независимых виджетов: если один упал, остальные 9 должны корректно отобразиться. |

## 4. Как реализовать повторные попытки (retry logic) для асинхронных операций с экспоненциальной задержкой?
Концепция Exponential Backoff (экспоненциальная задержка):
  При временных сбоях сети или перегрузке сервера повторные запросы отправляются не сразу, а с прогрессивно растущей задержкой:
  $$\text{Delay} = \text{BaseDelay} \times 2^{\text{attempt} - 1} \quad (+\text{случайный Jitter})$$
* Реализация:
  ```javascript
  async function retryWithBackoff(operation, maxRetries = 3, baseDelay = 300) {
      let lastError;
      for (let attempt = 1; attempt <= maxRetries; attempt++) {
          try {
              return await operation(attempt);
          } catch (error) {
              lastError = error;
              if (attempt === maxRetries) break;
              const delay = baseDelay * Math.pow(2, attempt - 1);
              await new Promise(resolve => setTimeout(resolve, delay));
          }
      }
      throw new Error(`Все ${maxRetries} попытки исчерпаны. Ошибка: ${lastError.message}`);
  }
  ```
  Это предотвращает эффект «лавины запросов» (Thundering Herd Problem), защищая сервер от перегрузки.

## 5. Что такое "состояние гонки" (race condition) в асинхронном коде и как его избежать?
Что такое Race Condition:
Ситуация, при которой корректность программы зависит от неконтролируемого порядка или времени завершения нескольких асинхронных операций.
Классический пример в UI: пользователь быстро вводит в строку поиска `"a"`, затем `"ab"`. Запрос для `"a"` задержался в сети на 1.5 секунды, а запрос для `"ab"` вернулся за 200 мс. В итоге сначала отрисуются результаты для `"ab"`, а затем их перезапишут устаревшие результаты запроса для `"a"`.
Способы предотвращения:
  1. Использование `AbortController`: отмена предыдущего незавершенного запроса перед отправкой нового:
     ```javascript
     let currentController = null;
     function onSearch(query) {
         if (currentController) currentController.abort();
         currentController = new AbortController();
         fetch(`/search?q=${query}`, { signal: currentController.signal });
     }
     ```
  2. Идентификатор актуального запроса (Request ID / Timestamp): сохранять счетчик последнего запроса и игнорировать ответы, чей ID меньше текущего.
  3. Паттерн Debounce: сдерживать отправку запроса до окончания ввода пользователем.

## 6. Как работает кэширование результатов асинхронных запросов и какие стратегии кэширования существуют?
Принцип работы: перед отправкой сетевого запроса проверяется наличие данных в локальном хранилище (`Map`, `sessionStorage`, `IndexedDB`, HTTP Cache). Если данные найдены и актуальны, они возвращаются мгновенно без обращения к сети. Если отсутствуют - выполняется сетевой запрос, результат сохраняется в кэш и отдается вызывающему коду.
Популярные стратегии кэширования:
  1. Cache-First (Сначала кэш): быстрый возврат из кэша. Сеть опрашивается только при промахе кэша (подходит для неизменяемых ресурсов: аватарки, справочники).
  2. Network-First (Сначала сеть): попытка получить самые свежие данные по сети; при ошибке сети (офлайн) отдаются данные из кэша.
  3. Stale-While-Revalidate (Устаревшее при ревалидации): немедленный возврат данных из кэша (мгновенный рендеринг), а в фоновом потоке отправляется тихий запрос в сеть для обновления кэша к следующему разу.
  4. TTL-кэширование (Time-To-Live): кэш хранит временную метку и считается устаревшим спустя $N$ секунд/минут.

## 7. Какие методы оптимизации производительности можно применить при работе с множественными асинхронными операциями?
1. Параллелизация независимых задач (`Promise.all`):
   Не использовать `await` последовательно там, где запросы не зависят друг от друга. Вместо $A + B + C = 3$ секунды параллельный `Promise.all` выполнится за $\max(A, B, C) = 1$ секунду.
2. Ограничение конкурентности (Concurrency Pool / Throttling):
   При обработке сотен задач (например, скачивание 1000 картинок) запуск всех разом может исчерпать сокеты браузера (лимит 6 соединений на домен) и перегрузить оперативную память. Используется пул воркеров (batching по 5–10 одновременных задач).
3. Отмена неактуальных задач (`AbortController`):
   Прерывание загрузки картинок, видео или данных, вышедших из зоны видимости (Viewport) или при закрытии модального окна.
4. Кэширование и дедупликация:
   Если два компонента на странице одновременно запрашивают одного и того же пользователя, создается один промис, результат которого отдается обоим компонентам.

## 8. Как обрабатывать ошибки в цепочках промисов и предотвращать "проглатывание" ошибок?
Предотвращение проглатывания ошибок (Swallowed Errors):
  * Ошибка возникает, если в блоке `.catch()` ошибка просто логируется без повторного проброса (`throw error`), из-за чего последующие `.then()` считают промис успешно разрешенным с результатом `undefined`.
  * Правило: если блок `.catch()` не восстанавливает работоспособное дефолтное состояние, он обязан повторно выбросить ошибку:
    ```javascript
    fetchData()
        .then(parseData)
        .catch(err => {
            logError(err);
            throw err; // Пробрасываем ошибку дальше по цепочке!
        });
    ```
* Глобальный перехват необработанных реджектов:
  Для отлова забытых ошибок на уровне окна используется обработчик события `unhandledrejection`:
  ```javascript
  window.addEventListener('unhandledrejection', (event) => {
      console.error('Необработанный реджект промиса:', event.reason);
  });
  ```

## 9. В чем преимущества использования async/await по сравнению с традиционными промисами и обратными вызовами?
1. Читаемость и структура: код выглядит синхронным, плоским и читается сверху вниз, избавляя от лесенки вложенных коллбэков (Callback Hell) и длинных цепочек `.then()`.
2. Единая обработка ошибок: единый блок `try...catch...finally` перехватывает как асинхронные ошибки сети, так и синхронные ошибки JavaScript (например, `JSON.parse` битого ответа). В цепочках промисов синхронная ошибка до первого `.then` могла уронить скрипт.
3. Удобная работа с циклами и условиями: внутри `async`-функции можно использовать привычные управляющие конструкции `for...of`, `while`, `if/else`, приостанавливая цикл на каждой итерации при необходимости (`await`). В промисах для этого требовались сложные рекурсивные конструкции.
4. Прозрачность стека вызовов (Stack Trace): стек ошибок при `await` содержит корректные имена функций и номера строк, в то время как в промисах стек часто терялся внутри анонимных функций внутри очереди микрозадач.

## 10. Как отлаживать асинхронный код и какие инструменты разработчика наиболее полезны для этого?
1. Async Stack Traces в Chrome/Firefox DevTools:
   Современные инструменты разработчика автоматически восстанавливают полный контекст вызовов сквозь границы асинхронных тиков и микрозадач (флаг *Async* в панели Call Stack).
2. Точки останова (Breakpoints):
   * Расстановка точек останова прямо на строках с `await` позволяет пошагово (Step Over / F10) наблюдать за изменением состояния переменных до и после завершения операции.
   * *Pause on caught/uncaught exceptions* для автоматической остановки в момент выброса исключения.
3. Панель Network:
   * Просмотр точных заголовков, тела запроса/ответа, HTTP-статусов, таймингов (TTFB, Content Download).
   * Вкладка *Throttling* для эмуляции медленного 3G-соединения или полного офлайна при тестировании лоадеров и Retry-логики.
4. Консольное логирование с таймстемпами:
   Использование `console.time('метрика')` и `console.timeEnd('метрика')` для точного замера параллельных и последовательных операций.
