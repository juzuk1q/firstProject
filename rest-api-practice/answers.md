### 1. Какие основные принципы REST архитектуры вы знаете?
REST (Representational State Transfer) — архитектурный стиль взаимодействия компонентов распределенного приложения, сформулированный Роем Филдингом.

| Принцип | Описание |
| :--- | :--- |
| Клиент-сервер (Client-Server) | Полное разделение интерфейса пользователя и логики хранения/обработки данных. Клиент и сервер эволюционируют независимо. |
| Отсутствие состояния (Statelessness) | В запросе от клиента содержится вся контекстная информация для его обработки сервером. Состояние сессии на сервере не сохраняется. |
| Кэшируемость (Cacheability) | Ответы сервера должны явно маркироваться как кэшируемые или некэшируемые (заголовки `Cache-Control`, `ETag`) для снижения сетевой нагрузки. |
| Единообразие интерфейса (Uniform Interface) | Стандартизированная адресация ресурсов по URI, использование стандартных HTTP-методов и самоописываемые сообщения. |
| Многоуровневая система (Layered System) | Клиент не знает, подключен ли он напрямую к конечному серверу или к промежуточным узлам (прокси, балансировщики нагрузки, CDN). |

### 2. В чем разница между HTTP методами PUT и PATCH?

| Критерий | `PUT` | `PATCH` |
| :--- | :--- | :--- |
| Характер обновления | **Полное замещение** существующего ресурса. | **Частичная модификация** (обновление конкретных полей). |
| Передаваемое тело | Клиент отправляет полную новую модель ресурса. Опущенные поля должны быть удалены или сброшены в `null`/значения по умолчанию. | Клиент отправляет только те ключи и значения, которые нужно изменить. Остальные поля ресурс сохраняет. |
| Идемпотентность | **Идемпотентен**: многократное повторение одного и того же запроса дает одинаковый результат состояния данных на сервере. | **Формально не гарантирует идемпотентность** (хотя на практике чаще всего пишется идемпотентно). |

### 3. Какие коды состояния HTTP наиболее часто используются в REST API?

| Код | Название | Когда возвращается |
| :--- | :--- | :--- |
| `200 OK` | Успешно | Запрос успешно выполнен (`GET`, `PUT`, `PATCH`, `DELETE`). |
| `201 Created` | Создано | Ресурс успешно создан (обычно ответ на `POST`). |
| `204 No Content` | Нет содержимого | Действие выполнено успешно, тело ответа отсутствует (часто для `DELETE`). |
| `400 Bad Request` | Неверный запрос | Ошибка валидации данных, неверный синтаксис JSON или отсутствуют обязательные поля. |
| `401 Unauthorized` | Не авторизован | Отсутствует или недействителен токен аутентификации. |
| `403 Forbidden` | Запрещено | Пользователь аутентифицирован, но прав доступа к ресурсу недостаточно. |
| `404 Not Found` | Не найдено | Запрашиваемый ресурс по указанному URI или ID отсутствует. |
| `409 Conflict` | Конфликт | Нарушение уникальности данных (например, дубликат email или ISBN). |
| `429 Too Many Requests` | Превышен лимит | Сработал rate limiter (слишком много запросов за промежуток времени). |
| `500 Internal Server Error` | Внутренняя ошибка | Необработанное исключение или аппаратный/программный сбой на сервере. |

### 4. Что такое ресурсо-ориентированный дизайн URL?
Ресурсо-ориентированный дизайн — это подход к проектированию API, при котором конечные точки (URL) представляют собой **сущности (существительные во множественном числе)**, а действия над ними выражаются **стандартными HTTP-глаголами**, а не действиями в URL.

- **Правильно (RESTful):**
  - `GET /api/books` — получить каталог книг
  - `POST /api/books` — добавить новую книгу
  - `GET /api/books/15` — получить книгу №15
  - `PUT /api/books/15` — полностью обновить книгу №15
  - `DELETE /api/books/15` — удалить книгу №15
- **Неправильно (RPC-стиль):**
  - `/api/getBooks`, `/api/addBook`, `/api/deleteBookById?id=15`

### 5. Какие преимущества предоставляет пагинация в API?
1. **Снижение сетевого трафика**: клиент не выкачивает мегабайты данных за один запрос при наличии тысяч записей.
2. **Оптимизация базы данных**: запросы используют операторы `LIMIT` и `OFFSET` (или cursor-based пагинацию), уменьшая нагрузку на RAM и процессор СУБД.
3. **Улучшение пользовательского опыта (UX)**: быстрая загрузка первых результатов в интерфейсе приложения вместо долгого ожидания полной выгрузки.
4. **Защита от DoS**: предотвращает исчерпание памяти Node.js процесса при чтении огромных массивов объектов.

### 6. Как организовать валидацию данных в REST API?
Валидация организуется как middleware перед вызовом бизнес-логики контроллера:
1. **Проверка обязательных полей и типов**: проверка наличия обязательных ключей (`title`, `author`, `isbn`) и их типов (`typeof`, `parseInt`).
2. **Проверка бизнес-правил**: контроль уникальности (например, отсутствие дубликатов `isbn` в базе), диапазона значений (год издания не может быть отрицательным или из далекого будущего).
3. **Использование библиотек**: применение стандартизированных схем валидации (например, `Joi`, `Zod`, `express-validator`).
4. При возникновении ошибки немедленно прерывается запрос и клиенту отправляется статус `400 Bad Request` с понятным описанием нарушенных полей.

### 7. Какие подходы к обработке ошибок в REST API вы знаете?
- **Централизованный middleware ошибок**: перехват всех необработанных исключений в одном месте приложения через `app.use((err, req, res, next) => ...)`.
- **Единый стандартизированный формат тела ошибки**: ответ всегда возвращает JSON одинаковой структуры, например:
  ```json
  {
    "error": "ConflictError",
    "message": "Книга с таким ISBN уже существует",
    "statusCode": 409,
    "timestamp": "2026-11-20T09:30:00.000Z"
  }
  ```
- **Кастомные классы ошибок**: наследование от `Error` (`NotFoundError`, `BadRequestError`, `ForbiddenError`) с привязкой конкретного HTTP-статуса к классу ошибки.
- **Разделение режимов**: подробный стек вызовов (`err.stack`) передается только в среде разработки (`NODE_ENV === 'development'`), а в проде скрывается для безопасности.

### 8. В чем разница между query parameters и path parameters?

| Критерий | Path parameters (параметры пути) | Query parameters (параметры строки запроса) |
| :--- | :--- | :--- |
| Место в URL | Являются частью структуры пути: `/api/books/:id` (`/api/books/42`) | Передаются после знака `?`: `/api/books?author=Толстой&page=2` |
| Обязательность | Как правило, строго обязательны для идентификации конкретного ресурса. | Необязательны (опциональны), имеют значения по умолчанию. |
| Назначение | Указывают на конкретную сущность или вложенный ресурс (`/users/1/orders/5`). | Используются для фильтрации, поиска, сортировки и пагинации выборки. |
