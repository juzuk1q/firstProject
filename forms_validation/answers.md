1.	Какие HTML5-атрибуты используются для клиентской валидации и какую функциональность они предоставляют?
- `required` - поле обязательно для заполнения.
- `minlength` / `maxlength` - минимальная и максимальная длина текста.
- `min` / `max` - границы для чисел и дат (в работе: `min="1900-01-01"` у даты рождения).
- `pattern` - регулярное выражение, которому должно соответствовать значение.
- `type` (`email`, `tel`, `date`, `number`, `url`) - проверка формата и подходящая клавиатура на мобильных.
- `step`, `multiple` и др.
Браузер сам проверяет эти ограничения и выставляет состояние в `field.validity` (`valueMissing`, `typeMismatch`, `tooShort`, `patternMismatch`…), а CSS-псевдоклассы `:valid` / `:invalid` позволяют их стилизовать.

2.	В чем разница между novalidate атрибутом формы и отключением валидации через JavaScript?
`novalidate` на `<form>` отключает только **встроенные всплывающие подсказки браузера** и блокировку отправки; сами ограничения (`required`, `pattern` и т. д.) остаются, и их можно проверить через `checkValidity()` и `validity`. Так мы получаем собственные сообщения об ошибках, не теряя возможностей Constraint Validation API. «Отключение через JS» (например, просто `preventDefault()` без проверок) убирает саму проверку - форма отправится с любыми данными. В работе использован `novalidate` + собственная проверка в `script.js`. Важно: клиентская валидация - это удобство, а не защита; сервер всё равно обязан проверять данные.

3.	Как правильно связать `<label>` с полем ввода и почему это важно для доступности?
Двумя способами: `<label for="email">Email</label>` + `<input id="email">` (совпадающие `for` и `id`) или вложить `<input>` внутрь `<label>`. Важность: скринридер зачитывает подпись при фокусе на поле; клик по тексту label ставит фокус в поле (или переключает чекбокс) — увеличивается область нажатия, что удобно на мобильных и людям с двигательными нарушениями. Placeholder заменой label не является.

4.	Какие типы полей `input` наиболее подходят для разных видов данных (email, телефон, пароль и т.д.)?
- `email` - почта (проверка формата, клавиатура с `@`); 
- `tel` - телефон (цифровая клавиатура, но без встроенной проверки формата - нужен `pattern`); 
- `password` - скрывает ввод; 
- `date` - календарь и проверка диапазона; 
- `number` - числа; 
- `url` - адреса; 
- `text` - имена и прочий текст; 
- `radio` - один вариант из группы; 
- `checkbox` - несколько вариантов или согласие; 
- `search`, `range`, `color` - по назначению.

5.	Как работает валидация с помощью `pattern` атрибута и в каких случаях его следует использовать?
Значение атрибута - регулярное выражение, которому должна соответствовать вся строка. Применяется там, где нет подходящего `type`: телефон (`\+?[0-9\s\-\(\)]{10,18}`), сложность пароля (`(?=.*[a-z])(?=.*[A-Z])(?=.*\d)\S+`), индекс, артикул. Пустое необязательное поле не проверяется. Рекомендуется сопровождать `pattern` понятным текстом ошибки, так как стандартное сообщение браузера неинформативно.

6.	Какие события JavaScript используются для реализации валидации в реальном времени и почему?
- `blur` - проверка, когда пользователь закончил ввод в поле: не ругаемся на недопечатанное значение.
- `input` - после первой ошибки перепроверяем на каждый символ, чтобы сообщение исчезало сразу при исправлении; также счётчик символов.
- `change` - для `select`, `checkbox`, `radio`, `date`, где `blur` неудобен.
- `submit` - финальная проверка всех полей; при ошибках отменяем отправку (`preventDefault()`) и переводим фокус на первое невалидное поле.

7.	Как обеспечить доступность сообщений об ошибках для пользователей скринридеров?
- Привязывать сообщение к полю через `aria-describedby` (id элемента с ошибкой).
- Ставить `aria-invalid="true"` на невалидное поле и снимать при исправлении.
- Контейнеру ошибки задавать `role="alert"` (или `aria-live="polite"`), чтобы текст озвучивался при появлении.
- Не передавать ошибку только цветом: рядом должен быть текст (в работе - текст под полем + красная рамка).
- После неудачной отправки переводить фокус на первое поле с ошибкой.
- Итоговое сообщение выводить в области с `role="status"`, а не через `alert()`.

8.	В чем преимущества использования fieldset и legend для группировки полей формы?
Это семантическая группировка: скринридер перед каждым полем группы озвучивает `legend` («Пол: Мужской»), что особенно важно для группы radio/checkbox, где у каждого варианта своя подпись, а у группы общий вопрос. Визуально разделяет большую форму на смысловые блоки («Личная информация», «Безопасность»), а атрибут `disabled` на `fieldset` отключает сразу все вложенные поля.

9.	Как реализовать кастомную валидацию для сложных случаев (например, подтверждение пароля)?
Сравнить значения в JS и вывести своё сообщение: если `confirmPassword.value !== password.value` - показать «Пароли не совпадают» и пометить поле. Проверку запускают на `input` в поле подтверждения **и** на `input` в поле пароля (если пароль изменили позже), а также при `submit`. Можно использовать и `field.setCustomValidity('Пароли не совпадают')` (пустая строка снимает ошибку): тогда поле участвует в `checkValidity()` и `:invalid`. В работе реализовано через функцию `getError()`, которая возвращает текст ошибки.

10.	Какие методы CSS используются для визуального отображения состояний валидности/невалидности полей?
- Псевдоклассы `:valid`, `:invalid`, `:required`, `:optional`, `:in-range`, `:out-of-range`, `:placeholder-shown`; `:user-invalid` / `:user-valid` - срабатывают только после взаимодействия пользователя.
- Классы `.error` / `.valid`, которые ставит JS (как в работе): красная/зелёная рамка, фон, `box-shadow`.
- `:focus` / `:focus-visible` - кольцо фокуса.
- Псевдоэлементы (`label.required::after{content: " *";}`) для отметки обязательных полей.
- Анимация `@keyframes shake` для привлечения внимания к ошибке (с отключением при `prefers-reduced-motion`).
